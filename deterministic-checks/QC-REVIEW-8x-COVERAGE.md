# Coverage of the 8.1-8.8 external QC review remediation list

An external QC review of this repo's benchmark output (the same review
`judge_determinism_config_lint.py`'s docstring and `PERPLEXITY-QC-FINDINGS.md` already
reference in part) issued an Immediate/Short-term/Medium-term remediation list, numbered 8.1
through 8.8. This document is the item-by-item disposition: what got fixed directly in the
pipeline, what got new coverage in this folder, what was intentionally dropped, and what is a
task-authoring fix rather than a pipeline fix. Written 2026-09-14, alongside the change that
implements the "pipeline" half of this list.

## How to read the "Fit" column

- **Pipeline fix** -- the defect is in shared infrastructure this repo owns (a grading-harness
  extractor, a converter, a reusable check script). Fixed here, benefits every task
  automatically going forward.
- **New check (this folder)** -- not fixable by changing shared code (the actual remedy is a
  per-task or per-criterion authoring decision), but the defect SHAPE is mechanically
  detectable. A new script surfaces it; a human still decides the fix.
- **Task-conversion fix** -- specific to one task's content (its script dependencies, its
  criterion wording, its source-file selection). No pipeline or check-script change closes
  this; it needs the task itself reworked.
- **Dropped for now** -- needs a harness capability this repo does not have yet, and building
  that capability wasn't judged worth doing as a side effect of this pass.

## Item-by-item

| # | Finding | Fit | Disposition |
|---|---|---|---|
| 8.1 | Recalculate submitted workbooks before extracting text (bias against the 3 lowest-scoring models; 28 submissions across 18 tasks graded with every calculation invisible) | **Pipeline fix**, plus a **new tool** for the retroactive gap | Root cause fixed directly: `pipeline/templates/harbor/verifier_lib/sources/xlsx.py`'s `extract_xlsx()` -- the actual per-task grading-sandbox extractor, shipped verbatim into every bundled task by `cycle.py bundle` -- now recomputes every formula cell with the `formulas` engine before falling back to the on-disk cache. `pipeline/gdpval_qc/converters.py`'s `_xlsx_to_text` (Internal QC's own conversion path) gets the identical fix. Both are additive/fallback-safe: any recompute failure degrades to the exact pre-existing cache-only behavior, never a hard failure. Verified against a synthetic stale-cache workbook (a plain openpyxl-saved file with one formula cell -- openpyxl itself always leaves such a cell's cache blank on save, reproducing the review's own described defect exactly): old behavior read the formula cell as `None`, the fixed extractor reads the correct recomputed value. **Gap this doesn't close**: tasks already bundled BEFORE this fix still carry the old extractor baked into their `tests/verifier_lib/` until re-bundled (`cycle.py bundle` re-copies the template fresh) -- and any deliverables already collected from a completed eval run (sitting in `03_evals/.../deliverables/`) were graded under the old behavior regardless. `workbook_recalc.py` (new, this folder) covers that retroactive case: point it at an already-collected batch of submitted workbooks and it patches the on-disk cache in place, verified end-to-end (dry-run report, apply, independent re-verify) against the same synthetic fixture -- so "only the grading pass repeats" (no model re-run needed) is achievable for already-collected batches, not just future ones. |
| 8.2 | Turn on multi-judge voting (`Config.models` already accepts 3; every task ships 1; temperature 1.0) | **Pipeline detection covered** (partially pre-existing); **remediation is a task-conversion fix** | `judge_determinism_config_lint.py` (already in this folder, pre-existing) already flags the temperature=1.0-with-no-panel half of this on real tasks -- confirmed by running it against this repo's own `pipeline/data/sample_corpus/task_11`, whose real `tests/verifier.json` has exactly this shape (`config.temperature: 1.0`, `config.models: ["openai/gpt-5.4"]`) and gets flagged. That lint's key-name patterns (`temperature`/`sample_count`/`panel`/`votes`/`repeats`) do not match a `models` field, so the single-model-list half of the same finding was a real, undetected gap -- closed here with the new `judge_panel_size_check.py`, also confirmed flagging the same real `task_11` config. Neither script can WRITE a fix: which 2 additional models to add to reach a real panel is a benchmark-owner decision about model diversity, cost, and rate limits that a script has no basis for making. Populating the panel, per task, is a task-conversion fix the team executes using these two scripts' output as the worklist. |
| 8.3 | Quarantine `task_298` and rebuild it (answer key grounded in two unshipped scripts, ~90% of marks unwinnable) | **Task-conversion fix** (that specific task), plus a **new check** for the pattern class | `task_298` itself needs an actual human decision (ship the scripts' outputs as inputs, or rewrite the tests to grade what the instruction asks for) -- not attempted here; this repo has no access to the two scripts' real outputs, and inventing a fix would be worse than leaving it flagged. What IS new: `golden_dependency_reachability_check.py`, which generalizes the pattern (a rubric criterion's expected value leaning on an analysis script/notebook not shipped under `environment/`) so the NEXT task_298-shaped defect is caught mechanically instead of by a full external review. Verified against a synthetic fixture reproducing the exact shape (a criterion citing `analysis4.py` and `sim_reins.py` by name, neither present in the environment) -- correctly flags both; correctly stays clean on the real `task_11` fixture, which has no such dependency. |
| 8.4 | Make truncation loud (9 deliverables silently cut; one task's reference answer 72.6% discarded; one task graded on 57-100% of different models' own work depending on verbosity) | **Pipeline fix** | Every text extractor under `pipeline/templates/harbor/verifier_lib/sources/` (xlsx, docx, pptx, pdf, csv, md, text) now appends an explicit `[TRUNCATED: ...]` notice into the returned text whenever the `max_content_chars` cap (default 90000) actually cuts content, via a new shared `_content_limits.py` helper. This is deliberately a THIRD option, not literally either of the two the review names (raise the cap / hard-fail the run): picking a new cap number is a cost/context-budget decision this fix doesn't make unilaterally, and hard-failing an entire eval run over one oversized deliverable is a bigger behavior change than this pass took on. What it does fix is the specific harm the review names -- "grading a quarter of a document while reporting a confident verdict" -- because the judge (human or LLM) now sees the cut directly in the graded text instead of a document that quietly stops mid-way. Verified: a real `task_11` docx run through a deliberately tiny limit now carries the notice; the same file at the real 90000-char default carries no notice (confirming the fix is silent when nothing was actually cut). If the team prefers raising the cap or hard-failing instead, that's a follow-up decision on top of this baseline, not blocked by it. |
| 8.5 | Convert ~44% mechanical reward to arithmetic (needs a `results.json` deliverable or a new `xlsx.read_cells` source command, plus numeric comparators) | **Dropped for now** | Explicitly out of scope for this pass per direct instruction. This is a harness CAPABILITY gap (a new source command + numeric comparator type), not a lint or a task fix -- there is no partial version of this worth shipping without the enabling work landing first. Left for a dedicated pass. |
| 8.6 | Cap conditions per check (~13% of rubrics at 8+ conditions, one at 27) | **New check (this folder)** | `criterion_condition_count_check.py` -- counts separately-checkable conditions per criterion (sentences, "and"/"or" outside parentheticals, semicolon/enumerated clauses) and flags anything over `--max-conditions` (default 3, the review's own recommended ceiling). Lint only, never rewrites a criterion. Verified against the real `task_11` fixture: 13 of its 17 criteria flagged over the 3-condition default, including one at 22 -- real signal on a real task, not just a synthetic pass. |
| 8.7 | Show the judge the inputs when detecting invention (one task's criterion judges invention vs. provided data from the candidate's memo alone) | **New check (this folder)** | `invention_detection_input_check.py` -- flags an invention/fabrication-detection criterion whose grading config shows the judge only the candidate's own deliverable (an `output/`-prefixed path), never anything under `environment/`. Verified against the real `task_11` fixture: 3 of its criteria (checking for "unsupported symptoms," "clinically supported findings," etc.) are graded from `output/clinical_note.pdf` alone, with the case's own source documents (`environment/data/nursing_handoff_note.docx`, `radiology_case_packet.pdf`) never in view -- the exact pattern the review described, found on a real task already in this repo. Cannot write a fix: which source file(s) belong on which criterion is an authoring call. |
| 8.8 | Fix misalignments between the verifier and instruction of each task | **Already covered** | This is the standing purpose of this folder's existing Check C/D scripts, not a new item: `environment_input_check.py` (instruction names an input the environment doesn't have, or vice versa), `deliverable_filename_check.py` (both directions: instruction vs. what judge.toml actually grades), `deliverable_count_check.py`, `tab_naming_check.py`, `rubric_text_lint.py`. No new script added for this line; route any surviving misalignment findings through the existing tools above. |

## What this adds up to

Two real defects are fixed at the root (8.1's grading-time formula blindness, 8.4's silent
truncation) rather than merely detected, because both turned out to live in code this repo
directly owns and ships into every task (`pipeline/templates/harbor/verifier_lib/` and
`pipeline/gdpval_qc/converters.py`) rather than in an external harness. Three genuinely new,
generalizable detection gaps are closed (8.2's panel-size half, 8.6, 8.7), one existing gap gets
a purpose-built generalization plus an explicit tool for its retroactive half (8.3, 8.1's
already-collected-batches case). One item (8.5) needs harness capability work not attempted
here. One item (8.8) needed nothing new. Every new script in this list is v1 and uncalibrated
against a real corpus at scale -- each was verified functionally (synthetic fixtures proving the
detection logic fires and stays quiet correctly) and, where the pattern exists in this repo's
own sample data, against a real task (`task_11`) -- but none has been run over hundreds of real
tasks the way this folder's pre-existing scripts have. Treat a finding from any of the five new
scripts as a lead to verify by reading the flagged criterion, not a confirmed defect.

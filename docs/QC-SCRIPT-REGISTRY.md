# Our QC scripts in plain English

<!-- Written from the main branch at commit 7e64189. Part of the plain-English QC documentation set; see the appendix of QC-SOP-first-run.md. -->

This guide explains every QC check we run on benchmark tasks, for readers who have never seen our system. It covers what each family of checks protects against, what the scripts do to find it, which scripts can stop a task and which only warn. The scripts that are not checks are in [QC-SCRIPT-REGISTRY-TOOLS.md](QC-SCRIPT-REGISTRY-TOOLS.md).

## How a task moves through our QC

A task is one work assignment that an expert writes for AI models. It has an instruction (the text the AI is told to follow), input files, a reference answer called the golden (the answer the author says is correct), and a grader called the rubric (a list of pass/fail criteria, each with a weight; an AI's score is the total weight of the criteria it passes). Our QC (quality control) starts after a task is fully built and packaged, not while the author is still writing it (SOP: docs/QC-SOP-first-run.md, section 6). A task goes through five stages in order. Stage 1 is the author pre-check: scripts (programs with fixed rules) scan the package, the author runs the golden through the grader locally twice, and an independent reviewer signs off. Stage 2 is the DataOS pipeline (DataOS is the platform that runs and grades tasks; a pipeline is a fixed chain of automated steps): it runs the golden itself, AI solvers and an empty answer through the grader. Stage 3 is four identical AI reviews that read the task package and the stage 2 results. Stage 4 is a manager (a person) who reads the outcome and the reviews. Stage 5 is the TFRL human QC team (TFRL is the team that does the final human check), who sample batches of 50 or more cleared tasks and accept or reject. A task is blocked (stopped and sent back) when a blocking script reports a fail or error at stage 1, or when any one of the four AI reviews reports a major finding at stage 3; a warning only tells the author to look and never stops a task. Scripts decide at stage 1, AI models decide at stage 3, and people decide at stages 4 and 5; stage 2 gives no verdict, it only produces evidence. Seven scripted checks call an AI model, and all seven only warn (counted by reading the check registries in deterministic-checks/svc_run_checks.py and deterministic-checks/ekw/ekw_run_checks.py: none of the seven maps any result to "fail"). Passing our stages is not a TFRL approval; it means scripts, AI models and a person checked the known defect classes.

### Glossary

| Term | Plain meaning |
|---|---|
| Task | One work assignment for an AI model: an instruction, input files, a golden and a rubric. |
| Instruction | The text file (instruction.md) that tells the AI what to produce. |
| Golden | The reference answer the author wrote. A good rubric gives it full marks. |
| Rubric | The grader: a list of criteria that each pass or fail an answer. |
| Criterion | One pass/fail test inside the rubric, for example "the memo states the total refund amount". |
| Weight | How much one criterion counts. An answer's score is the sum of the weights of the criteria it passes; weights should total 1.0. |
| Oracle run | A DataOS run in which the golden itself is graded by the rubric. It should score full marks. ("Oracle" is the platform's name for the reference answer.) |
| Empty-answer run | A DataOS run in which an empty answer is graded. It should score zero. |
| AI solver run | A DataOS run in which an AI model attempts the task and its answer is graded by the rubric. We use Terminus-2 and Codex, both on GPT 6 Sol. |
| Major | A defect where a correct answer that follows the instruction loses credit, or a wrong or empty answer gains credit. Any major in any one of the four AI reviews fails the task. |
| Minor | Any other defect worth reporting. It does not fail a task. |
| Blocking | A script result of fail or error that stops a task and sends it back to the author. |
| Warn | A script result that tells the author to look. It never stops a task. |
| Prefilter | A script that runs first on a built package to catch cheap problems early (svc-pc-pipeline/tools/svc_prefilter.py); some of its rules block and some warn. |
| Gate | A stop point a task must clear before it moves on, such as deterministic-checks/pre_submit_gate.py, which runs the gate scripts before an author submits. |
| DataOS | The Turing platform that stores tasks, runs AI models on them, grades the runs, and runs the AI reviews. |
| TFRL | The human QC team that samples each batch of cleared tasks and accepts or rejects them. The pipeline and our scripts are not TFRL. |
| EKW | One of our two task sets. Its checks are registered in deterministic-checks/ekw/ekw_run_checks.py. |
| SVC | Our other task set. Its checks are registered in deterministic-checks/svc_run_checks.py. |

### What the review prompt of the normal pipeline (saved prompt 431) does

The prompt text is not in the repository; the saved prompt lives in DataOS (the SOP, docs/QC-SOP-first-run.md section 6b, only gives its number: saved prompt 431, whose DataOS name is Comprehensive_v3_pipeline_quality_re-derive_cascade_NOP_2026-10-03, used by the pipeline named "ManualQC automated QC pipeline 4 Reviewers" (DataOS pipeline 141, version 8, spec 401), with Claude Opus 5.5 at medium effort).md, section B), not the prompt text itself, so it could not be checked against code. The review prompt (saved prompt 431) is the instruction given to each of the four reviewing AI models (the review type is called "Answer Check"). It asks only for defects that could cost correct work 0.10 or more of the total weight, or let an empty or copied answer score 0.20 or more, and tells the reviewer to ignore style, packaging and a single low-weight strict criterion. First, reading only the instruction and the inputs, the reviewer works out the 3 to 6 key answers itself, using code for every number, and records every reasonable reading where the instruction allows several. Second, it compares those answers with the rubric and the golden, looking for a grader value that is less defensible than its own, a grader that accepts only one of two readings, or a golden that is wrong or rests on a fact no file states. Third, it adds up the weights of every criterion a careful expert would also fail, and keeps the finding only at 0.10 or more or if it touches the main decision. Fourth, every criterion of weight 0.03 or more must match a sentence in the instruction and must not be forbidden by another one; criteria that demand things never asked are grouped and kept at 0.10 or more. Fifth, an empty-answer run that scores 0.20 or more is a finding. Sixth, a criterion that every AI solver run failed is a defect at any weight if their work meets the instruction's words, but a solver miss on something clearly asked is not a defect. The output is one verdict, reject if any finding survives, each with the instruction sentence, the criterion id, the weight and the evidence. The DataOS rule on top is that a task is sent back if any one of the four reviews has a major (docs/QC-SOP-first-run.md, section 6b step 3, and docs/task-review-rules-v2.md).

The prompt names seven finding types. The one-line meanings below are taken from the draft; the prompt itself does not define them. All examples are invented.

| Finding type | Plain meaning | Invented example |
|---|---|---|
| READINGS | The instruction allows two reasonable readings and the grader accepts only one. | Two documents give different headcounts and the instruction does not say which governs; the grader accepts only the first document's number. |
| WRONG_VALUE | The grader expects a number that the sources support less well than the reviewer's own number. | The grader expects a 12 percent margin; the reviewer's recomputation from the sources gives 14 percent. |
| GOLDEN | The golden is wrong, double counts, or rests on a fact no file states. | The golden applies a 5 percent supplier discount that no input file mentions. |
| CONFLICT | A criterion contradicts the instruction. | The instruction says "do not estimate missing months" and a criterion requires a full-year estimate. |
| UNASKED | A criterion demands something the instruction never requests. | A criterion requires a "Key Risks" section when the instruction only says "summarise concerns". |
| WEAK_GRADER | An empty answer scores 0.20 or more. | A criterion "no unsupported claims appear" passes an empty file. |
| GRADER_BUG | The grader could crash, time out or misread a valid answer. | The grader reads a spreadsheet formula cell that has no stored value as blank and fails a correct total. |

## How to read these tables

- A **task** is one work assignment for an AI model: an instruction, input files, a reference answer called the **golden**, and a **rubric** (the grader: a list of pass/fail criteria, each with a weight). A **criterion** is one pass/fail line of the rubric.
- **EKW** and **SVC** are our two task sets. SVC tasks keep their rubric in `tests/deliverables*/judge.toml` (a TOML settings file the grader reads; each file lists the output files its criteria read, under `files=`). EKW tasks keep their rubric in `tests/verifier.json` (a JSON file where each entry is one grading check). In both, `instruction.md` is the prompt the solving AI reads, `environment/` holds the inputs it is given, and `solution/` holds the golden.
- **Blocks** means the script can report `fail`. SOP section 6a (`docs/QC-SOP-first-run.md`, lines 472 to 479) says a task goes to DataOS (the platform that runs and grades our tasks) only with "no fail or error" from the checks. **Warns** means the script can at most report `warn`, a note that never stops a task on its own (`deterministic-checks/ekw/ekw_run_checks.py`, docstring: "`warn` ... never blocks on its own").
- **Where it runs**, four stages:
  - *Author pre-check*: the task author runs the two runner scripts, `deterministic-checks/ekw/ekw_run_checks.py` (EKW) and `deterministic-checks/svc_run_checks.py` (SVC), which run every registered check (SOP section 3 and 5).
  - *Pre-submit gate*: the stop point before any upload (SOP section 6a): the same runner, plus `svc-pc-pipeline/tools/svc_prefilter.py` (a script that scans a package before it is zipped), plus `deterministic-checks/pre_submit_gate.py`, which runs `harbor_rubric_gate.py` and `reward_signal_gate.py` (two rule sets, described below). A runner check therefore runs at both the first and second stage.
  - *DataOS return*: the step that reads results back after the DataOS review chain. None of the checks in families 1 to 4 run there.
  - *After DataOS*: also none in families 1 to 4.
- "Both" in the EKW, SVC column means the check is registered in both runners. We counted this by parsing the `CHECKS` dictionary of each runner with Python's `ast` module (a short Python script): the EKW runner registers 51 checks, the SVC runner 45, 52 distinct names. All 21 registered checks used in families 1 to 4 appear in both.
- An **AI-model check** calls an AI model and, in this repo, only ever warns.
- **rewardkit** (also written reward-kit): the third-party grading library (`harbor-rewardkit`) that reads `judge.toml` files and scores a run. A "rewardkit package" is an SVC-style task graded through it. **Harbor** is the task format DataOS uses (defined in QC-SCRIPT-REGISTRY-TOOLS.md); names such as harbor_rubric_gate and "native-harbor" refer to it.

### Family 1: The prompt, files and package disagree

- **What goes wrong:** the prompt tells the solver to save one file name and the grader opens another; the prompt names an input file that was never shipped; the grader file list points at a file that is not in the package; the package carries stray files or breaks a format rule the platform requires, so a correct answer scores zero or the task cannot be judged.
- **What the scripts do to find it:** compare file names written in `instruction.md` with the `files=` lists in the grader, with the real folders, and with the files the golden cites; count the deliverables the prose promises against the ones the grader checks; look for URLs standing in for inputs; check that every input and output is written as a full path, that a do-not-train marker line (a "canary" line: a fixed sentence marking the text as benchmark data) is present, that there is no role-play opener, no stray golden files, and that a spreadsheet output has a sheet and column description in the prompt; one AI-model check reads the prompt, the file lists and the folder listing for six patterns.
- **Example (invented):** `instruction.md` says "save the result as Q3_Review.xlsx" while the grader opens `Review_Q3.xlsx`. An AI that obeys the prompt writes the wrong file and scores zero.
- **Blocks and warns:** deliverable_filename, deliverable_count, environment_input, three harbor_rubric_gate rules and svc_prefilter's file-list and Dockerfile rules can block. unrequested_deliverable_source, source_citation_existence, structural_audit, task_metadata_completeness and spelling_grammar only warn. mojibake_check blocks only on grader file-list hits (see its row).

### Family 2: The AI under test can see the answer (leaks)

- **What goes wrong:** an answer figure sits in a file the solver is given, a file is named like an answer key, the golden file itself is in the solver's workspace, the rubric text copies the golden's own sentences, or the prompt carries build-system text. The solver then copies the answer instead of working it out.
- **What the scripts do to find it:** search the prompt for file names that look like answer files; search the input files for the numbers the rubric expects, and fail only when the matching file's own name looks like an answer file (words such as golden, solution, answer, key, reference, rubric, cheat); compare runs of consecutive identical words between each criterion and the golden files; open hidden file parts (cell comments, defined names, tracked changes, headers and footers, speaker notes); compare byte fingerprints of workspace files with golden files.
- **Example (invented):** an input spreadsheet has a cell comment reading "Answer: churn is 4.2 percent", and the rubric expects 4.2 percent churn.
- **Blocks and warns:** a confirmed hit blocks. A list of three or more numbers found in both a rubric and an input only warns.

So for these scans "Blocks" means "can contribute a major finding", not "stops the task by itself". We did not trace the full blocking set.

### Family 3: The golden is wrong, invented or unreadable

- **What goes wrong:** the golden's totals do not add up from the sources, it names a vendor or figure no file mentions, it cites a source file that does not exist, or its file is corrupt. A correct AI answer then fails, or a wrong one passes.
- **What the scripts do to find it:** recompute total columns in golden spreadsheets from the input tables; open every golden file with a program for its file type (spreadsheet, Word, PDF) and report files that fail to parse; two AI-model checks look for named facts and figures no input file backs; two scans look for golden citations of files that are absent, and for golden facts built on a source marked draft or unreconciled.
- **Example (invented):** the golden says refunds total 4,500 and the order list adds up to 3,900.
- **Blocks and warns:** golden_arithmetic and deliverable_integrity can block. The two AI-model checks only warn.

### Family 4: The grader asks for what cannot be known or was never asked

- **What goes wrong:** a criterion needs a fact the inputs do not contain, a naming scheme only the grader knows, a tab position the golden itself lacks, a script or tool the solver was never given, a date the prompt never states, or a banned word the task's own sources use. # Script registry, part B: families 5 to 8

Terms used in this section, each defined once here:
- A **task** is a work assignment written for AI models. It has an instruction (the prompt), input files, a reference answer called the **golden**, and a grader called the **rubric**: a list of pass/fail criteria, each with a weight.
- A **verifier** is the grader's configuration file. SVC tasks keep it in `judge.toml`; EKW tasks keep it in `tests/verifier.json`. The AI judge that reads the answer against a criterion is configured there, including the list of files it may read (`files=`).
- A **lint** is a script that scans text or files for known bad patterns. A **gate** is a stop point a task must clear before it moves on. A **prefilter** is a quick script run before a package is built into an upload zip.
- An **LLM** (large language model) is an AI text model. Checks marked "AI" below call one and only ever warn.
- **DataOS** is the platform that runs and grades tasks. A **pipeline** is a fixed chain of automated steps. **TFRL** is the human QC team that samples our tasks after our own checks.
- "Registry" means the `CHECKS` table in `deterministic-checks/ekw/ekw_run_checks.py` (EKW) or `deterministic-checks/svc_run_checks.py` (SVC). We counted the registry entries with a python3 AST (syntax tree) parse of each file: 51 EKW entries, 45 SVC entries. A registry result of "fail" or "error" blocks the task (SOP, `docs/QC-SOP-first-run.md`, step 6a, item 1); "warn" never blocks.
- "Where it runs" uses: **author pre-check** (the registry runners, SOP steps 3 to 5), **pre-submit gate** (SOP step 6a: `svc_prefilter.py`, `pre_submit_gate.py`, `svc_coverage_trace.py`, `svc_preship_gate.sh`), **DataOS return**, **after DataOS**. None of the scripts in families 5 to 8 run at the DataOS return step. Only `reward_signal_gate.py` G6 can also read finished DataOS run workbooks (`--evidence`), so it can also run after DataOS.

### Family 5: The grader is too rigid
- What goes wrong: a criterion demands an exact value, count, name, cell address, layout, calculation order or formula count that the prompt left open. A correct answer written another way loses credit.
- What the scripts do to find it: pattern matching finds decimals with no tolerance words, "exactly" language, a number plus a cell address, and prompt-quoting rules that force a case to fail. Four AI checks read the prompt next to the criteria and ask whether a pinned detail has support in the prompt, whether a different calculation order reaches the same answer, or whether fixing one criterion left a twin unfixed. One script reads sibling criteria for an accepted alternative that another criterion takes back. One lints the hand-written formula-authenticity checker some tasks ship.
- Example (invented): the prompt says "work out the monthly cost per seat". A criterion says "Expected: 21.40 (Summary!C9)". An answer with 21.4 in another tab fails, and so does one that rounds to 21. Another criterion requires "at least 12 live formulas" because the golden has exactly 12.

### Family 7: The AI judge cannot see what it grades
- What goes wrong: each group of criteria has an AI judge that reads only the files listed for that group. Too narrow a list: a criterion such as "matches the source price list" is graded from the answer's own word. Too wide a list: source files sit beside the answer, so a blank answer earns credit from the sources. Also, the judge's text view misses formulas, number formats and tab colours; a file over 1 MiB (1,048,576 bytes) is replaced by "[skipped: file too large]"; and long workbook text is cut at a character cap.
- What the scripts do to find it: they compare each judge's file list with the files named in the prompt and in each criterion, check that every listed file exists and fits, estimate the text size of the golden workbook against the cap, match criteria that need a property the judge's extraction command cannot show, and check the judge's own instructions mark source text as untrusted. One AI check asks whether a criterion implies a source the list lacks.
- Example (invented): the file list holds only `memo.docx`, but a criterion says "totals match the supplier price sheet". Or the list holds the memo plus seven source documents, and a blank memo scores 0.5 because the judge finds the answer in the sources.
- Blocks and warns: all of these block except `judge_scope_under_inclusion` (AI), `judge_file_size_cliff`, `source_truncation`, and the low-headroom half of `xlsx_extraction_budget`.

### Family 8: Formulas that look blank to the grader
- What goes wrong: a spreadsheet cell holds a formula (for example `=B4/B2`) but the file never stored the computed result. The judge reads stored results only, so it sees an empty cell and fails a criterion such as "margin is 14 percent" for a correct answer. Some formulas also recalculate to an error or the wrong value.
- What the scripts do to find it: one script recalculates every formula in the golden workbooks with the `formulas` Python library, ignoring stored values. A second mode opens each graded workbook as the grader's reader does and counts formula cells with no stored value. A gate check confirms the grader's own reading library recalculates uncached formulas. A scan lists golden cells with an empty stored result.
- Example (invented): "Net margin" holds `=B4/B2` with no stored value. The grader sees blank and the criterion "margin is 14 percent" fails.
- Blocks and warns: the recalculation check, the stored-value mode and the library check block; the recalc-step advisory only warns.

### Family 9: Duplicate or overstuffed criteria

- **What goes wrong:** One fact is graded two, three or four times under different criterion names, so it counts far more than its intended weight. Or several facts are packed into one pass/fail criterion, so a solver who gets five of six right earns zero, and the LLM judge may decide differently on identical answers. Or two criteria share a name, and a program that stores criteria by name keeps only one and silently drops the other's weight. Or one group of criteria is so long that the grader itself crashes.
- **What the scripts do to find it:**
  - They split each criterion's text into clauses (at semicolons, "and", numbered lists and sentences) and count them.
  - They compare the text of criteria with each other: word-overlap scores, or an identical requirement sentence.
  - They compare criterion names.
  - They count criteria per group.
- **Example (invented):** A shipping task has criteria r012, r019, r027 and r033. All four say "the shipping log has no per-parcel key". The fact is graded four times, so about four times its intended share of the score rides on one observation.
- **Blocks and warns:**
  - Block: `compound_criterion` at 3 or more clauses on a must-pass criterion of weight 0.10 or less (4 or more clauses for EKW); `same_file_requirement_duplicate`; `judge_criterion_name_duplicate`; EKW build check `duplicate_verifier_name`; reward-signal gate G5 and G7 (unless the author writes a recorded disposition); prefilter "grammar bomb" (more than 15 criteria in one group); `svc_rubric_static_check.py` (more than 20); `judge_group_size_scan.py` (more than 24).
  - Warn: `duplicate_criterion_content` (it can never fail; its fail tier was removed, `duplicate_criterion_content_check.py` lines 705 to 711); the 2-clause and "tiered credit" findings of `compound_criterion`.
- **Placement note:** the group-size limits (15, 20, 24) protect against a grader crash, so they could also sit in Family 11. They are here because the cure is the same as for an overstuffed rubric: fewer criteria per group.

### Family 10: Scoring set-up wrong or unstable

- **What goes wrong:** The numbers that turn pass/fail verdicts into a score are wrong or inert. Weights do not add to 1.0. Declared weights for each deliverable group are never applied. A "must-pass" criterion is just words in a description, so failing it does not zero anything. The grader is asked once at a random setting, so the same answer scores differently on two runs. The grader's library versions are not fixed, or two requirement files disagree about them, so installs fail or drift.
- **What the scripts do to find it:**
  - They read the rubric and scoring files and recompute weight sums.
  - They compare each group's declared weight with the weight table in `tests/reward.toml` (the file that says how groups combine).
  - They search the parsed config for temperature and sample-count fields.
  - They count how many judge models are listed.
  - They read `pip install` lines and requirements files.
  - They diff the two requirements files.
- **Example (invented):** Two requirement files in one task pin different versions of the same PDF library. The grader's environment is rebuilt from one file, the install fails, and every run scores 0.0. That looks like a very hard task but it is a broken package.
- **Blocks and warns:**
  - Block: `rubric_schema` weight checks; `weight_application`; `judge_determinism_config_lint` when it flags a task; `verifier_requirements_pin_mismatch`; G9; `judge_panel_size_check`; EKW build-check weight findings (`weight_not_numeric`, `weight_sum_off` beyond 0.01); the post-run `weight_aggregation_check` and `certification_gate_check`.
  - Warn: `harness_fragility`; `dependency_pin`; EKW build-check `weights_all_missing`, `verifier_count_low`, `config_missing`, `config_no_models`, and `weight_sum_off` between 0.001 and 0.01.
- **Placement note:** `rubric_schema` also checks blank descriptions, placeholder "Expected:" values and stub text. Those parts could sit with a family about unreadable criteria; only the weight parts belong here.

### Family 11: The package will not build or run

- **What goes wrong:** The task folder cannot be built into a sandbox, or its grader cannot execute. Required files or folders are missing. The golden folder is empty or a golden file has zero bytes. A criterion reads a file no golden provides. `tests/test.sh` has Windows line endings, so its first line names an interpreter that does not exist. The build recipe pulls data from storage DataOS cannot reach. The container recipe is missing. The package is zipped with the wrong top folder. The grader would run longer than its time limit.
- **What the scripts do to find it:**
  - They list the package's files and check that each required one exists and is not empty.
  - They check every file a criterion reads against the golden folder.
  - They read the raw bytes of `tests/test.sh` for carriage-return line endings.
  - They replay the golden through the task's own grader code, with the LLM judge replaced by a stub that approves everything.
  - They search the `Dockerfile` for lines that cannot work on DataOS, and read the zip's member list.
  - They total the environment size and compare to 35 MB (`DEFAULT_THRESHOLD_BYTES`, `environment_size_budget_check.py` line 289).
  - They multiply criteria by judge samples by 46 seconds and compare to the time limit.
- **Example (invented):** A task's `Dockerfile` runs `dvc pull`, a data-download command that needs a credential DataOS never supplies. The image build errors before any grading starts, so every run of the task fails the same way.
- **Blocks and warns:**
  - Block: the EKW build check's fail findings; `verifier_executability`; prefilter HARD rules (`dvc pull`, `files=` path missing, `lease.json`); `container_build_check`; `package_shape_check`; `timeout_headroom_check`; Harbor gate `no_extraneous_files` and `solve_sh_scope`.
  - Warn: `environment_size_budget` (as wired in both runners); prefilter junk, mojibake and CRLF rules; EKW build-check warnings.
- **Placement note:** the group-size limits that crash the grader sit in Family 9. A corrupt or unreadable golden file (`deliverable_integrity_check.py`) is a Family 3 problem and is not listed here.

### Family 12: Run results contradict the package (after DataOS)

- **What goes wrong:** The golden does not earn full marks from its own grader. Repeated oracle runs on the same golden bytes disagree. A grader crashes, runs out of time, or hits a schema-too-large error, so the score came from the grader failing, not from the answer. A Comprehensive Review (an older DataOS review step, see note below) did not end in a valid result.
- **What the scripts do to find it:**
  - They read the result files downloaded from DataOS: `reward.json` or `reward.txt`, `reward-details.json`, `verifier-report.json` (per-criterion judge votes), `trial.log`.
  - They compare the oracle runs of one task with each other.
  - They search the verifier output for Python tracebacks, "rewardkit exited 1", "Reward '<group>' failed", "compiled grammar is too large" and "timed out after".
  - They check that each review reply parses to the expected structure.
- **Example (invented):** Two oracle runs on the identical golden score 1.0 and 0.96. One criterion, v6c, passed on all 3 judge samples in one run and on 1 of 3 in the other. That criterion is a coin flip on our own answer.
- **Blocks and warns:**
  - Block: `comprehensive_review_evidence_gate` (it returns `fail` and `pre_submit_gate.py` exits 1 on it); `oracle_reproducibility_check` only when run with `--exit-nonzero-on-fail`.
  - Warn: `oracle_reward_details_audit` (always warn or pass, never fail).

## Method and what we could not verify

- Counting method: registry sizes by `ast` parse of the two `CHECKS` dictionaries (a short Python script). No other counts are asserted. Numbers quoted from file docstrings (for example "69 of 79", "45 of 45", "74 of 75") are the file's own claims; we did not re-derive them, because that needs real task packages.
- No check script was run. Statuses and thresholds come from reading the code (`classify_compound`, `check_task`, the registry `verdict` lambdas).
- Cases where the file's docstring and code disagree: G7 threshold (docstring 4, code 5); `svc_run_checks.py` count (docstring 41, code 45); `verifier_executability` docstring calls the EKW gold replay a "hard gate" while its own measured caveat says most failures were staging artefacts.
- Not read in full: `certification_gate_check.py` (1,761 lines; verdict rules from its header only), `compound_criterion_check.py` clause-splitting details, `weight_aggregation_check.py` body, and how `gate_playbooks.py`, `gate_verdict.py` and `build_review_union.py` use the scan scripts that mention `cross_group_duplicate_scan`, `judge_group_size_scan` and `judge_schema_bytes`.
- Where `timeout_headroom_check.py`, `judge_panel_size_check.py` and `criterion_condition_count_check.py` are called in the live process is not stated in the SOP: README or `run_all.py` mention only.

### What needs a run, and what we cannot see

Because we run the task and read the results, we can catch defects that a checker reading only the files cannot:

- A golden that fails its own grader. The DataOS oracle runs grade the golden itself and it should score full marks; the manager treats fewer than two full-mark oracle runs as "cannot judge yet" (docs/task-review-rules-v2.md). Locally the author also runs the golden through the grader twice (svc-pc-pipeline/tools/judge_emulate.py, SOP section 6a step 5).
- An empty answer that earns credit. The empty-answer run should score zero, and the four AI reviews record any score of 0.20 or more of total weight as a finding (the review prompt, saved prompt 431, as described above).
- A criterion that every AI solver failed even though they followed the instruction. The reviews read the grader's stated reason for each such criterion and call it a task defect if the solvers' work meets the instruction's words (SOP section 6a step 4).
- A grader that crashes, times out, or gives different scores to the same answer. deterministic-checks/oracle_reward_details_audit.py reads the downloaded result files for Python tracebacks and "timed out after" text, and for an oracle score below 1.0.

Because we recompute and trace with scripts, we also catch:

- Wrong golden figures: deterministic-checks/golden_arithmetic_check.py recomputes total columns in golden spreadsheets from the source tables, and deterministic-checks/formula_health_check.py recalculates formulas (check names from the registries in deterministic-checks/svc_run_checks.py and deterministic-checks/ekw/ekw_run_checks.py).
- Requirements nobody grades: svc-pc-pipeline/tools/svc_coverage_trace.py numbers each instruction requirement and rejects a map that skips one.
- On a resubmission, svc-pc-pipeline/tools/svc_eval_regrade.py re-grades the real AI answers against the fixed rubric: a wrong answer that scored full marks must now fail, and a correct answer that lost points must now pass.

What we do not check (confirmed by searching the scripts under deterministic-checks/ and svc-pc-pipeline/tools/ for each topic; the review prompt (saved prompt 431) is not in the repository, so its own scope is taken from the draft):

- Whether made-up input data looks realistic (for example sequential ids, round numbers, a template look). No script tests this. The only hits for these words are inside other checks' own comments.
- Prose style or AI-sounding wording. The only wording check is deterministic-checks/spelling_grammar_check.py, which checks spelling and warns only.
- Whether a persona is stated. No script checks for one. The one related rule fails an instruction that opens with a role-play line such as "You are a ..." (deterministic-checks/harbor_rubric_gate.py, check instruction_concision).
- Difficulty. No script blocks a task for being too easy; a manager notes it, and TFRL treats headroom (how hard the task is for models) as information, not a pass or reject criterion (docs/QC-SOP-first-run.md, section 8).
- Whether a task is novel, interesting or agentic. No script of ours covers it.

### Known limits

- The pass and catch rates of the four-review setup come from tests on 271 tasks and are not yet audited. docs/task-review-rules-v2.md says to quote no catch rate or false-flag rate unless it is labelled early and unaudited, with its denominator and date, so this document gives none.
- Some scripts have produced false alarms. The hidden-metadata leak check (deterministic-checks/metadata_leak_check.py, which opens cell comments, tracked deletions and speaker notes) flagged 32 of 600 tasks as fail on its first full run, and its own documentation says every distinct flagged pattern was hand-verified and none was a real leak; the answer-value leak check (deterministic-checks/answer_key_content_leak_check.py) says its false positives could not be driven to zero and treats it as a low-confidence tool. The numbers are from those files' own header text, not re-run by us.
- The DataOS review rule fails a task on any one major in any of the four reviews, with no step to confirm the finding first. The reviews can disagree. The author must read the review that found it and either fix a real problem or explain in writing why it is a false positive.
- The return tools that record results (svc-pc-pipeline/tools/svc_dataos_returns_parse.py, svc_record_return.py, ekw_record_return.py) were patched on 2026-10-05 (pull request 94): earlier copies read a `checks` list, but Answer Check replies carry a `findings` list, so the old tools read none of the real answers. A task now passes only if it has at least two reviews and every returned review is parsed with zero majors; any major or unparsed review fails it.
- A pass through our stages is not a TFRL approval, and it does not mean the task has no defects.
